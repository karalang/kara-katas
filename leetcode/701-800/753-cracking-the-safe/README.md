# 753. Cracking the Safe

A safe has a password of `n` digits, each from 0 to k - 1. It checks the
last `n` digits typed after every digit, and opens as soon as they
match. Return any shortest string of digits that is certain to open the
safe, whatever the password.

```
n = 1, k = 2  ->  "10"      (or "01")
n = 2, k = 2  ->  "01100"   (or "00110", "10011", "11001")
```

**Constraints:** 1 <= n <= 4; 1 <= k <= 10; 1 <= k^n <= 4096.

## Approaches

Every one of the k^n codes must appear in the string, and after the
first n digits each digit can add at most one new code, so no answer is
shorter than k^n + n - 1 digits. That length is always reached: an
answer of that length is a de Bruijn sequence written out with its first
n - 1 digits repeated at the end. The arms find one in four different
ways, and they do not give the same string.

| file | mechanism |
|---|---|
| `crack_safe.kara` ★ | an Euler circuit by Hierholzer's method, with the (n-1)-digit strings as nodes, held as numbers, and each code as an edge; an explicit stack; O(k^n) |
| `crack_safe_search.kara` | the textbook search: from n zeros, type the smallest digit that makes a new code, taking digits back when stuck; codes and text stay strings, in a `Set[String]` |
| `crack_safe_lyndon.kara` | the Lyndon words whose length divides n, written out in order (Fredricksen, Kessler and Maiorana), generated by recursion |
| `crack_safe_greedy.kara` | Martin's rule: from n zeros, always type the largest digit whose code is new, with the codes marked in a `Vec[bool]` |
| `differential.kara` | the four arms against the definition on every allowed safe, four properties |

Since the arms give different strings, what every arm prints is the
answer judged rather than the answer itself: for nine safes, among them
both LeetCode examples, k = 1 and the largest allowed, the answer's
length, whether that is the shortest possible, and whether every code
appears in it exactly once; then the same over all 38 safes the
constraints allow. All four arms print the same 10 lines.
`crack_safe.py` mirrors the ★ arm and its output is byte-identical.

## Differential

`differential.kara` holds copies of the four arms and the definition,
which reads every n-digit window of the answer into a `Set[String]` and
requires each of the k^n codes, written out as strings, to be in it. The
constraints allow only 38 safes, so the differential checks every one of
them, 12,291 digits of answer for each arm.

| | property |
|---|---|
| P1 | the answer is k^n + n - 1 digits long, the shortest possible |
| P2 | every code is in the answer (the definition) |
| P3 | the answer ends with its own first n - 1 digits, as a de Bruijn cycle written out does |
| P4 | in its first k^n digits, each digit from 0 to k - 1 appears k^(n-1) times |

It prints `38 safes (12291 digits in all), 4 arms, 608 checks,
0 failures` under `karac __mir-run` and `karac __mir-llvm-run`, and the
same under `karac __mir-llvm-asan` with no error.

## Mutation testing

Twelve edits to the differential, three to each arm, each run under
`karac __mir-run`. Eleven are killed by failed checks and one stops the
run with an error. Three more edits, E1 to E3, change nothing that can
be seen, and the differential rightly reports no failure for them.

| # | mutation | failures by property |
|---|---|---|
| M1 | ★: the circuit's last edge not written | P1 38, P2 38, P4 10 |
| M2 | ★: the largest digit never taken from a node | P1 38, P2 38, P4 35 |
| M3 | ★: n zeros written first, not n - 1 | P1 38, P4 34 |
| M4 | search: the starting code not marked as typed | P1 38, P4 34 |
| M5 | search: a code taken back left marked as typed | P1 25, P2 25, P3 25 |
| M6 | search: stopped one code short | P1 34, P2 34, P4 34 |
| M7 | Lyndon: only words of length n written | stops |
| M8 | Lyndon: the largest digit never used | P1 34, P2 34, P4 34 |
| M9 | Lyndon: the start written again from the cycle's end, backwards | P2 25, P3 25 |
| M10 | greedy: the largest digit never tried | P1 34, P2 34, P4 34 |
| M11 | greedy: the starting code not marked | P1 38 |
| M12 | greedy: each digit written one too high | P2 34, P3 25, P4 34 |
| E1 | ★: the root's marker -2, not -1 | 0 |
| E2 | Lyndon: one more unused slot | 0 |
| E3 | greedy: the digit loop run while d > -1 | 0 |

P1 and P2 between them kill eleven of the twelve, and M7 stops the run:
written with only the Lyndon words of length n, the cycle is empty for k
= 1, and writing its start again divides by its length. P3 sees only the
edits that break the cycle's wrap: M5, whose search ends on a text that
is not a cycle, M9, which writes the wrong digits after the cycle, and
M12, whose digits run past k - 1. P4 sees M1 to M4, M6, M8, M10 and
M12, which change which digits make up the first k^n; M11 only types one
code twice at the end, which P1 alone sees. E1 marks the root with
-2 instead of -1, and it is still not written; E2 keeps one more slot
that nothing reads; E3 writes the digit loop's test as d > -1. Two first
choices were replaced. M4 was the search never trying the largest digit:
with no way to type every code the search backtracks through every
order, and the run did not finish, so it was stopped. M9 was the Lyndon
arm writing its start again from the cycle's second digit, and that edit
changes nothing: the cycle starts with n zeros, so its digits 1 to n -
1 are the same as its digits 0 to n - 2.

## Verification

Every arm prints the same output as `crack_safe.py` under `karac
__mir-run` (the v2 MIR interpreter) and `karac __mir-llvm-run`, and
under `karac __mir-llvm-asan` (AddressSanitizer) with no error; the
differential prints its line under all three. `karac check` passes all
four arms, the differential and the bench program. The search and Lyndon
arms were first written without `mut` on the calls that hand a `mut ref`
parameter on to the next level; `karac check` refuses that (every
argument to a mutating parameter is marked), and `karac fix` added the
six markers. The debug build that runs `__mir-llvm-run`,
`__mir-llvm-asan` and `build --mir` and the release build that runs
`check` and `__mir-run` are both at kara `b84c5d937f`, whose last
compiler change is `56a4cad109`. The runtime archives were built after
the last runtime change, `b09cd37112`.

Since kara `3c8e763161` (B-2026-10-18-31) the sanitizer lane sees leaks
itself. The leak check also copied each arm's and the differential's
lane executable as it was linked and ran it with the preloaded shim from
kata 708, which refuses the lane's hand-made stack so that LeakSanitizer
sees `main`: all five print their output and report no leak.

The frozen legacy backends refuse all four arms at type checking, at the
harness's `*` over a vector's `iter()` (`*c`), since legacy gives those
by value where v2 gives references. The legacy interpreter runs the
differential and prints the same line, but legacy `karac build` refuses
it in code generation, at the search arm's `typed[..].to_string()` on a
`mut ref String` ("element TypeExpr unknown"), the shape of the
relocated B-2026-10-06-79. It accepts the bench program. Legacy is
frozen, so this is noted, not filed.

## Benchmarks

The bench program uses the ★ arm in all five languages. It cracks every
one of the 38 allowed safes in each of 2,000 rounds, adding up the
digits of the answers and a checksum of their text. Every implementation
prints `76000 safes: 24582000 digits in all, checksum 306599605`, the
Kāra program under `karac __mir-run` included (in 67 s).

Spot timings on a shared 4-core container, eight runs of each compiled
program, five of them interleaved, and two of Python (`bench.sh` timings
need a quiet machine):

| | time |
|---|---|
| C (`clang -O3`) | 0.34 to 0.38 s |
| Rust (`rustc -O`) | 0.35 to 0.47 s |
| Rust (`rustc -O -C overflow-checks=on`) | 0.40 to 0.44 s |
| Go | 1.05 to 1.13 s |
| Python | 6.6 s |
| Kāra (`karac build --mir`) | 0.42 to 0.47 s |

`bench.sh` builds the Kāra program with `karac build --mir`, the
v2 compiled backend, the one this kata measures now that legacy is
frozen. That edit is by hand, on top of the `scripts/new-bench.sh`
output. Under `karac __mir-llvm-run` the program prints the same line in
2.3 s, compile included; that JITs the MIR's IR without optimization
passes, so it is not a benchmark.

So at the medians of the interleaved runs the v2 build takes 0.44 s,
against C's 0.35, Rust's 0.40 (0.42 under overflow checks) and Go's
1.07. Under valgrind's cachegrind v2 runs 3.1 billion instructions
against C's 1.4 billion and Rust's 2.6 billion, with few mispredicted
branches in any of them (0.7 to 0.9%). The legacy build of the same
program ran 0.30 to 0.44 s, a median of 0.39 s in the interleaved runs,
so v2 takes about 1.1 times legacy's time, inside M2's limit of twice
legacy; new katas' benches are outside M2's frozen set in any case. The
comparison with C and Rust waits until after M4.

## Compiler findings

None filed. `String` has no `pop` or `truncate` in the library
(docs/library/strings.md), on either backend, so the search arm takes a
digit back with `typed = typed[..typed.len() - 1].to_string()`. That is
the library as specified, not a compiler gap; it is noted here because
backtracking over a string is common.
