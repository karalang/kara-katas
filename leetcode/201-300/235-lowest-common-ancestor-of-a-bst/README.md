# 235. Lowest Common Ancestor of a Binary Search Tree

Given a BST and two values `p` and `q` that are present in it, return the value
of their **lowest common ancestor** (LCA) — the deepest node having both `p` and
`q` as descendants, where a node is a descendant of itself.

## Approach

The BST ordering collapses this to a single root-to-split walk — no parent
pointers, no second pass. Starting at the root, at each node:

- both `p` and `q` **less than** the node → the LCA is in the **left** subtree;
- both **greater than** the node → the LCA is in the **right** subtree;
- otherwise the two search paths diverge here (or one value *is* this node), so
  this node is the split point and therefore the LCA.

`O(h)` time, `O(1)` extra space (`h` = tree height).

The tree is an **index pool** (`Vec[Node]` with `i64` `left`/`right`, `-1` =
null), built by BST insertion from a value list — the same shape as
[#230](../230-kth-smallest-element-in-a-bst/).

## Files

- [`lca_bst.kara`](lca_bst.kara) — Kāra implementation.
- [`lca_bst.py`](lca_bst.py) — Python mirror (oracle); same tree, same output.

Expected output (both): `6 2 4 2 8 2 5 4` (one per line).

**Workload.** Build-once + punch: one 200 000-node BST built from LCG values,
then 8 000 000 root-to-split LCA walks. The query count is high because a single
walk is only O(h) ≈ 35 steps; at lower counts the one-off tree build dominated
the measurement (at 400 k queries it *was* most of the runtime). Query pairs are
drawn from the inserted values, so both endpoints are always present and every
walk ends at a real split point. Sink = `198558594`.

**Tree shape is deliberate.** LCG values give a randomly shaped BST of depth
≈ 2·log₂ n ≈ 35. A sorted input would degenerate it into a 200 000-deep chain —
a completely different cost profile, and a stack hazard for the kata's recursive
insert.

### Mirror-parity note

All four lanes use an **index-pool tree** — an array of structs with `i64` child
indices and `-1` for null — rather than pointer-linked nodes (`Box`, `*Node`,
`unsafe.Pointer`). That keeps the pointer-chasing behaviour identical: every
lane does the same array-index dereference per step, so none gets an allocator
or locality advantage the others don't.

The benchmark builds the tree **iteratively** where the kata inserts
recursively. That is a setup-only difference — the measured `lca` walk is
byte-identical to the kata's — and it keeps 200 000 recursive descents out of a
timing story that is meant to be about the query.
