# 290. Word Pattern

Given a `pattern` of letters and a space-separated string `s`, decide whether the
letters map to the words following a **bijection**: each letter maps to exactly
one word and each word to exactly one letter, position by position.

`"abba"` + `"dog cat cat dog"` → true; `"abba"` + `"dog dog dog dog"` → false
(`a` and `b` would both map to `"dog"`).

## Approach

Split `s` into words, reject a length mismatch, then walk pattern and words in
lockstep with **two** maps — letter→word and word→letter. A conflict in *either*
direction (a letter already bound to a different word, or a word already bound to
a different letter) breaks the bijection.

## Compiler surfaces exercised

A deliberately collection/string-heavy kata: `Map[i64, String]`, `Map[String, i64]`,
`Vec[String]`, String equality, and `u8 as char` when building words from a
`Slice[u8]`. It surfaced a real compiler gap — `u8 as char` (the one infallible
integer→char cast) was wrongly rejected at typecheck, and the interpreter left it
an integer rather than a character — fixed in the sibling `kara` repo (ledger
`B-2026-07-24-3`).

## Files

- [`word_pattern.kara`](word_pattern.kara) — Kāra implementation.

**Workload.** Build-once + punch: 8 pattern/subject pairs built once — 1000
positions each over a 26-letter alphabet, subjects ~4900 characters. Even pairs
are a valid bijection, so the full 1000-position loop runs and returns true.
Odd pairs repeat the **first** word in the **last** position, colliding with a
letter already bound to it — so those scan everything too before failing.
Neither path is an early exit. 2500 punches, sink weights successes by
iteration. Sink = `1563750`, identical across all five languages.

Kāra sits **1.54× behind Rust** and 1.60× behind Go. Overflow checks are again
free (218.1 vs 225.5 ms, inside σ) — the work is string building, hashing and
allocation, not arithmetic.

### C's 7.34× is a data-structure difference, not a codegen one

Do not read the C column as "C is 7× faster than kāra at this problem." Two
choices in the C mirror account for nearly all of it, and both are what a C
programmer would genuinely write:

- **`p2w` is a direct-address array**, not a hash map. Pattern letters are
  byte-valued, so C indexes `val[letter_code]` directly and skips hashing
  entirely. Kāra, Rust, Go and Python all use a real map for that direction.
  (The `w2p` direction *is* an open-addressing hash map in C, since word keys
  are strings.)
- **C does no per-word heap allocation.** `split_words` copies each word into a
  preallocated static `words[1000][8]` buffer; the other four allocate an owned
  string per word, 1000 of them per punch.

Word Pattern is insert-only within a call — it never deletes — so unlike
[#291](../291-word-pattern-ii/README.md) there are no tombstones and no
probe-chain growth. That #291 mirror bug (tombstones plus `snprintf` plus
per-call `strlen`, together 3.1×) is deliberately avoided here: string copies
use `memcpy` and lengths are computed once.

The **kāra-vs-Rust 1.54×** is the like-for-like number on this kata: both
allocate owned strings per word and both hash both directions.
