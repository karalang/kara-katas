# 260. Single Number III

Exactly two elements of `nums` appear once; every other appears twice. Return the
two singles, in `O(n)` time and `O(1)` space.

## Approach

1. **XOR everything** → `x = a ^ b` (paired elements cancel). Since `a ≠ b`, `x`
   is non-zero.
2. **Isolate its lowest set bit** `bit = x & (-x)`. `a` and `b` differ in that
   bit, so it splits the array into two groups — one holding `a`, the other `b`,
   with each duplicate pair landing together in one group.
3. **XOR each group** independently → the two singles fall out.

Result sorted ascending for a deterministic line.

## Files

- [`single_number_iii.kara`](single_number_iii.kara) — Kāra implementation.
- [`single_number_iii.py`](single_number_iii.py) — Python mirror (oracle).

Expected output (both): `3 5` / `-1 0` / `0 1` / `4 12` / `5 8` (one pair per line).

**Workload.** Build-once + punch: four arrays of 200,002 `i64` (100,000 LCG
values written twice, plus two loners outside the value range) built once, then
2600 punches of the full two-pass algorithm — XOR-reduce the whole array, take
the lowest set bit, then partition-XOR it again. Each value's twin sits ~100k
elements away, so the partition branch sees a fresh bit per element instead of
a run of adjacent equal values. Sink = `573145098`, identical in all five
languages.

| Lane | mean ± σ | vs kāra |
|---|---|---|
| **kāra** | **311.4 ms ± 11.9** | — |
| rust | 436.3 ms ± 18.1 | 1.40× slower |
| c | 449.8 ms ± 38.6 | 1.44× slower |
| rust (overflow-checks=on) | 463.3 ms ± 46.0 | 1.49× slower |
| go | 2553.6 ms ± 56.2 | 8.20× slower |

**Do not quote that table on its own.** Kāra looks 1.44× ahead of C, and it
isn't — the lead is an ISA-baseline artifact, and this kata is what surfaced
that corpus-wide caveat.

### The kāra "win" is a CPU-baseline artifact, measured

`karac build` targets **`x86-64-v3`** (Haswell+, AVX2) by default — a
deliberate deploy-baseline commitment in the language design
(`cpu-baseline = "v3"`). `clang -O3` and `rustc -O` at *their* defaults target
**`x86-64` v1** (SSE2). Both loops here vectorize, so the two baselines are not
measuring the same machine.

Rebuilding C and Rust at kāra's baseline, all four in one hyperfine session
(30 runs, 5 warmup):

| Lane (all at `x86-64-v3`) | mean ± σ |
|---|---|
| c `-march=x86-64-v3` | 321.2 ms ± 24.3 |
| rust `-C target-cpu=x86-64-v3` | 325.6 ms ± 29.9 |
| kāra (default) | 334.8 ms ± 21.9 |
| rust `overflow-checks=on` + v3 | 339.1 ms ± 24.5 |

**A four-way tie inside 1.06×.** The 1.44× lead is entirely gone. The
symmetric check agrees: forcing kāra down with `--target-cpu=x86-64` gives
0.42 s against its 0.31 s default, and its AVX2 instruction count in `main`
drops from 59 to 0.

The honest reading of this kata is therefore: **kāra ties C and Rust at equal
ISA baseline on a vectorizable bitwise kernel, and its default build is a
1.4× win over a default `clang -O3` / `rustc -O` build** — which is a real
shipping-defaults difference worth knowing, but is not a codegen-quality claim.

### Go is 8× behind, and that is not a baseline artifact

Go's `gc` compiler has no autovectorizer at any flag setting, so its 2553.6 ms
is scalar code against everyone else's SIMD. That gap is real and unfixable
from the command line — it is the one place in this corpus where the ISA axis
genuinely separates a language rather than a build flag.

### The two loops, split

Deleting the partition pass (keeping only the XOR reduce) gives C 0.16 s and
kāra 0.16 s — a dead tie. All of the default-build difference lives in the
partition loop, and it is not branch misprediction: feeding uniform data, so
the branch is perfectly predicted, leaves both ratios unchanged.
