# 242. Valid Anagram

Return whether `t` is an anagram of `s` — i.e. they contain the same characters
with the same multiplicities.

## Approach

Over a lowercase-ASCII alphabet this is a single frequency pass: keep a 26-slot
count, bump it **up** for each letter of `s` and **down** for each letter of `t`.
`t` is an anagram exactly when every count returns to zero (a length mismatch is
rejected up front, so the counts only need to confirm equal multiplicities).
`O(n)` time, `O(1)` space.

## Files

- [`valid_anagram.kara`](valid_anagram.kara) — Kāra implementation.
- [`valid_anagram.py`](valid_anagram.py) — Python mirror (oracle).

Expected output (both): `true false true false true false` (one per line).

> **Host:** the canonical lane is Apple M5 Pro (6P+12E),
> [`bench/results.json`](bench/results.json), measured 2026-11-02 with karac
> g96fca5370 (0.8.0-dev.14215, the v2/MIR backend) — the file
> `scripts/consolidate-bench.sh` feeds into the top-level chart; its tables lead
> each subsection below. The tables labelled **x86 container snapshot** are an
> older shared x86-64 Linux cloud container run, kept as
> `bench/results.container-x86.json`, and are history. Absolute milliseconds are
> NOT comparable between the two hosts; only the **within-file cross-language
> ratios** are.

**Workload.** Build-once + punch: 8 string pairs of 20 000 lowercase characters
built once, `t` being `s` reversed (same multiset, so an anagram). Odd-indexed
pairs shift a single character, breaking the multiset without changing the
length. 8000 punches. The counting loop has **no early exit**, so true and
false cases do identical work and only the final 26-slot check differs. Sink =
`16004000`, identical across all five languages.

This is one of the **cleanest like-for-like comparisons in the corpus**: the
kata is a fixed 26-slot frequency array, so every language runs the same data
structure. There is no direct-address-vs-hash-map or allocation divergence to
caveat, unlike [#290](../290-word-pattern/README.md) and
[#291](../291-word-pattern-ii/README.md).

### ⚠️ At equal safety, kāra beats Rust here

> *2026-11-02: no longer true on the M5. On the MIR backend Kāra is 1.07×
> behind `rustc -O -C overflow-checks=on` (it led 0.89× on the 2026-07-28 M5
> feed), and overflow checks cost Rust 1.18× there, not 1.87× — see the M5
> table above and [`B-2026-11-02-3`](../../../../kara/docs/bugs-v2.md). The
> analysis below is the x86 container snapshot.*

This is the **first kata in the corpus where the equal-safety lane flips the
ranking**, and it is the comparison BENCHMARKS.md asks for:

| Comparison | Result |
|---|---|
| kāra vs `rustc -O` (silently wraps) | kāra **1.63× slower** |
| kāra vs `rustc -O -C overflow-checks=on` | kāra **1.15× faster** |

Turning overflow checks on costs Rust **1.87×** on this workload — 200.1 ms →
373.5 ms. That is not noise; it is 13 σ apart.

The reason is that this kata is **arithmetic-bound**, unlike every other kata
benched in this batch. The inner loop is two array reads, two subtractions and
two increment/decrement stores, 20 000 times per punch, with no hashing and no
allocation. Overflow checking lands directly on the hot instruction. On
[#290](../290-word-pattern/README.md), [#291](../291-word-pattern-ii/README.md),
[#332](../../301-400/332-reconstruct-itinerary/README.md) and
[#347](../../301-400/347-top-k-frequent-elements/README.md) the checks were
free (inside σ) precisely because those workloads are dominated by hashing and
allocation instead.

Kāra checks integer overflow **by default** and cannot be asked not to. So
`rust -O`'s 200.1 ms is a number for a program with different semantics, and
`rust_ovf`'s 373.5 ms is the like-for-like one. Both are reported above rather
than only the flattering one.

### Note on the Python lane

The Python mirror is committed as the correctness oracle but is intentionally
not a measured lane; `bench.sh` leaves it behind the `KARA_BENCH_INCLUDE_PY`
gate. Its algorithmic parity was verified at reduced scale: `ITERS=40` gives
sink `420` from both Python and Rust.
