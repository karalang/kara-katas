# 264. Ugly Number II

An **ugly number** has only 2, 3, and 5 as prime factors (1 counts). Return the
`n`-th ugly number (1-indexed).

## Approach

Every ugly number after 1 is `2×`, `3×`, or `5×` a *smaller* ugly number, so
build the sequence in order with three merge pointers into the results so far —
one each for the ×2, ×3, ×5 streams. Each step takes the smallest of the three
candidates, appends it, and advances **every** pointer whose candidate equalled
it (advancing all ties dedupes values reachable two ways, e.g. `6 = 2×3 = 3×2`).
`O(n)` time and space.

## Files

- [`ugly_number_ii.kara`](ugly_number_ii.kara) — Kāra implementation.
- [`ugly_number_ii.py`](ugly_number_ii.py) — Python mirror (oracle).

Expected output (both): `1 12 15 24 36 80` (one per line).

**Workload.** There is nothing to build once — the DP table *is* the work, and
it is rebuilt from scratch every punch. So this is a punch loop over a
**varying** `n`: 12,000 calls with `n` cycling over `[9000, 12000)`, which also
stops any of the five compilers hoisting a pure call with a constant argument.
`n` stays under 12,200 because the 12,200-th ugly number is ~5.08e18 — every
`dp[i] * 5` candidate still fits `i64`, so kāra's checked multiply never traps.
Sink = `369380900`, identical in all five languages.

### It is an if-conversion choice, and C's default is the wrong one

The three pointer advances are the whole story:

```kara
if c2 == next { i2 = i2 + 1i64; }
if c3 == next { i3 = i3 + 1i64; }
if c5 == next { i5 = i5 + 1i64; }
```

`clang`, `gcc` and `rustc` all **if-convert** these to branchless `sete` + `add`.
That looks like the good transform and here it is the bad one: `i2` feeds the
address of the *next* iteration's `dp[i2]`, so making the increment a data
dependency welds it onto the loop-carried address chain — load → lea → cmp →
sete → add → next load. `karac` leaves them as branches, so the predictor
speculates the next address and the loop runs at throughput instead of at
latency.

Disabling if-conversion in gcc confirms it outright:

| Build | mean |
|---|---|
| `gcc -O3` (branchless, its default) | 0.59 s |
| `gcc -O3 -fno-if-conversion -fno-if-conversion2` | **0.17 s** |

**3.5× from one flag**, and it also settles the ranking honestly: a C build
that makes the same choice kāra makes is **2× ahead of kāra**, not 1.78×
behind. What kāra wins here is the *default*, not the ceiling.

The residual 0.33 s vs 0.17 s is the safety axis. Kāra's inner loop carries, per
iteration, three bounds checks (`cmp`/`jae` on `dp[i2]`, `dp[i3]`, `dp[i5]`),
three multiply-overflow checks (`jo` after each `imul`), and three
increment-overflow checks (`jo` after each `inc`) that the C loop does not. The
increment ones are the same bounded-accumulator class as
[`B-2026-07-26-1`](../../../../kara/docs/bug-ledger.md) — `i2`/`i3`/`i5` are
monotone and bounded by `dp.len()`, so those three checks are provably
removable.

### The mirror-parity trap this kata sets

C is the only language here without a growable vector, so the naive mirror uses
one static buffer and skips the allocation the other four pay. This mirror
instead does `malloc` + `realloc` doubling per call, matching Kāra's `Vec.new()`,
Rust's `Vec::new()` and Go's `append`. It costs C almost nothing — removing the
realloc entirely (allocate `n` upfront, delete the grow branch) gives 0.58 s
against 0.59 s — so the allocation half of this workload is not where the time
goes, but the mirror is honest either way.
