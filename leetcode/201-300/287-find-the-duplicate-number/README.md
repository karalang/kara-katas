# 287. Find the Duplicate Number

`nums` has `n+1` values in `[1, n]`, so by pigeonhole at least one repeats. Find
it **without modifying** the array and in `O(1)` extra space.

## Approach

Read index `i` as a pointer to index `nums[i]`. Every value lies in `[1, n]`, so
walking these pointers from index 0 stays in-bounds; because a value repeats, two
indices point to the same place, making the functional graph contain a cycle
whose **entrance is the duplicate**. Floyd's tortoise-and-hare:

- **Phase 1:** advance `slow` by 1 and `fast` by 2 until they meet in the cycle.
- **Phase 2:** reset one walker to the start; advance both by 1 — they meet at the
  cycle entrance = the duplicate.

`O(n)` time, `O(1)` space, array untouched.

**Workload.** Build-once + punch: four 200,001-element arrays built once, then
80 punches of the kata's `find_duplicate` unchanged.

The array construction is the interesting part. A naive #287 input gives a
functional graph whose cycle is only `O(√n)` long, so Floyd would do ~600 hops
per call and measure nothing. Each array here instead encodes a **single
n-cycle over a shuffled order**: Fisher-Yates a list of `1..=n` with an LCG,
then set `arr[order[k]] = order[k+1 mod n]`. The walk from index 0 traverses
all `n` values in shuffled order — **~3n dependent loads** (slow does `n`, fast
does `2n`) over a 1.6 MB working set, every load address depending on the one
before it. `arr[0]` enters the cycle at a different member per array, so the
duplicate — the cycle entrance — differs and the sink is not a constant.
Sink = `8846215`, identical in all five languages.

### Runtime — 30 runs, 5 warmup

| Lane | mean ± σ | vs kāra |
|---|---|---|
| rust (overflow-checks=on) | 323.6 ms ± 17.9 | 1.05× faster |
| go | 328.7 ms ± 13.6 | 1.03× faster |
| c | 330.1 ms ± 17.6 | 1.03× faster |
| rust | 332.3 ms ± 17.3 | 1.02× faster |
| **kāra** | **339.3 ms ± 33.2** | — |

**A five-way dead heat — 1.05× from first to last, well inside σ.** This is the
tightest spread in the corpus, and it is tight for a structural reason rather
than a coincidence: the workload is **pure load-to-use latency**. Nothing here
can be vectorized, unrolled, or prefetched — each address comes out of the
previous load — so every compiler's output converges on "issue the load, wait."

That makes this kata the corpus's useful *null result*: on a memory-bound
pointer chase, choice of language buys nothing. Note in particular that
`rust_ovf` is nominally first and `rust` fourth, which is not a real ordering —
it is what a 1.05× spread against ±5% σ looks like.

It also tells you something about Kāra's bounds checks: the walk does three
bounds-checked index operations per iteration (`nums[slow]`, `nums[nums[fast]]`)
and they cost nothing measurable, because the branch predictor and the load
latency hide them completely. Bounds checks are expensive when they gate a
vectorizable loop; here there is nothing for them to gate.
