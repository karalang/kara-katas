# 279. Perfect Squares

Return the least number of perfect-square numbers (`1, 4, 9, 16, …`) that sum to
`n`.

## Approach

Bottom-up DP over amounts. `dp[i]` = fewest squares summing to `i`:

```
dp[0] = 0
dp[i] = 1 + min over all squares j² ≤ i of dp[i − j²]
```

Every amount is one square added to a smaller amount, so scanning all squares
`j² ≤ i` and taking the minimum builds the table in `O(n·√n)` time, `O(n)` space.

## Files

- [`perfect_squares.kara`](perfect_squares.kara) — Kāra implementation.
- [`perfect_squares.py`](perfect_squares.py) — Python mirror (oracle).

Expected output (both): `3 2 1 2 1 3 1` (one per line).

**Workload.** Nothing is built once — the DP table *is* the work, rebuilt from
scratch every punch. So this is a punch loop over a **varying** `n`: 100 calls
with `n` cycling over `[25000, 30000)`, which also stops any of the five
compilers hoisting a pure call with a constant argument. Each call grows a
fresh vector to `n+1` and, for every amount `i`, scans every square `j² ≤ i`
reading `dp[i - j²]` at a stride that widens with `j` — a nested-loop DP with a
non-sequential but cache-resident read pattern. Sink = `133748984`, identical
in all five languages.

### Runtime — 30 runs, 5 warmup

| Lane | mean ± σ | vs kāra |
|---|---|---|
| c | 210.7 ms ± 6.4 | 1.73× faster |
| rust | 211.4 ms ± 5.1 | 1.72× faster |
| go | 253.2 ms ± 20.6 | 1.44× faster |
| rust (overflow-checks=on) | 359.3 ms ± 8.0 | 1.01× faster |
| **kāra** | **363.8 ms ± 21.0** | — |

**Kāra is last here, and the whole gap is checked arithmetic.** It ties the
equal-safety Rust build to within 1.3% — inside σ — and both sit 1.72× behind
the two builds that wrap silently. Go, which bounds-checks but does not
overflow-check, lands in between at 1.44×, which is exactly where a
checks-but-no-overflow-checks language should sit.

This is the corpus's standard equal-safety picture, not a codegen deficit: at
matched safety Kāra and Rust are indistinguishable.

### Where the 1.7× goes, measured

The inner loop is three checked operations deep. Unchecking them one at a time
in the Rust mirror (everything else still `overflow-checks=on`):

| Build | mean |
|---|---|
| `rust_ovf` — everything checked | 0.36 s |
| … with only `j * j` unchecked | 0.31 s |
| … also with `dp[…] + 1` unchecked | 0.26 s |
| `rust -O` — nothing checked | 0.21 s |

So the loop-condition multiply is worth ~0.05 s, the inner add another ~0.05 s,
and the remaining ~0.05 s is spread across `i - j*j`, the counters, and `i + 1`.
No single statement dominates the way the accumulator does in
[#137](../../101-200/137-single-number-ii/) — this is checked arithmetic being
uniformly a bit expensive in a loop that is nothing but arithmetic.

`j * j` is worth a note: `j` climbs only until `j² > i ≤ 30000`, so it never
exceeds 174 and the multiply provably cannot overflow — but the bound comes
from the loop's *own exit condition*, which makes it harder to establish than
the loop-trip-count bound in
[`B-2026-07-26-1`](../../../../kara/docs/bug-ledger.md). Recorded here as an
observation, not filed as a second ledger item.

### Mirror-parity notes

- **C** allocates a fresh growable buffer per call (`malloc` + `realloc`
  doubling) rather than reusing one static array, matching Kāra's `Vec.new()`,
  Rust's `Vec::new()` and Go's `append`.

  (`KARA_BENCH_INCLUDE_PY` defaults to `0`).
