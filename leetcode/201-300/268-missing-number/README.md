# 268. Missing Number

`nums` holds `n` distinct values from `[0, n]`, so exactly one value in that range
is absent. Return it in `O(n)` time, `O(1)` space.

## Approach

XOR-fold every index `0..n` together with every array value. Each present value
cancels against its matching index, leaving only the one index whose value never
appeared — the missing number. XOR avoids the overflow the Gauss-sum method risks
(Kāra checks integer overflow by default, so XOR is the clean choice).

## Files

- [`missing_number.kara`](missing_number.kara) — Kāra implementation.
- [`missing_number.py`](missing_number.py) — Python mirror (oracle).

Expected output (both): `2 2 8 1 0` (one per line).

> **Host:** the first two tables below are the canonical Apple M5 Pro lane,

> `scripts/consolidate-bench.sh` feeds into the top-level chart. Everything after
> them is a shared **x86-64 Linux cloud container** snapshot, kept as
> `bench/results.container-x86.json`, and is history. Absolute milliseconds are
> NOT comparable between the two hosts; only the **within-file cross-language
> ratios** are.

**Workload.** Build-once + punch: four 1,000,000-element arrays built once —
each a permutation of `[0, n]` with a different value omitted — then 850
punches of the XOR fold in rotation. The fold is order-independent, so the
values are written at stride-coprime positions purely so the read pattern is
not a straight `arr[i] == i` identity that invites a peephole. Sink =
`434228253`, identical in all five languages.

### Runtime — Apple M5 Pro, sequential lane

Apple M5 Pro (6P+12E), 2026-11-02, `karac 0.9.0-dev.14057+g6697158fa` (v2/MIR
backend), hyperfine 30 runs, `KARAC_AUTO_PAR=0`.

| Lane | mean ± σ | vs kāra |
|---|---|---|
| c | 86.1 ms ± 0.9 | 1.02× faster |
| **kāra** | **87.9 ms ± 1.2** | — |
| rust | 90.0 ms ± 1.0 | 1.02× slower |
| rust (overflow-checks=on) | 90.3 ms ± 0.9 | 1.03× slower |
| go | 442.6 ms ± 5.5 | 5.03× slower |

On arm64 there is no ISA-baseline gap to explain away: **kāra is level with C**
(1.02× behind, about one σ) and 1.02–1.03× ahead of the two Rust builds. Go is
5.0× behind, scalar against everyone else's SIMD (see below). Against the
previous feed (2026-07-27, `karac 0.1.0`, legacy backend) every ratio is flat —
Kāra/Rust 0.96× → 0.98×, Kāra/C 1.00× → 1.02×, Kāra/Go 0.19× → 0.20× — while
every comparator ran 14–19% slower in absolute terms (machine state).

### Runtime — 30 runs, 5 warmup

| Lane | mean ± σ | vs kāra |
|---|---|---|
| **kāra** | **328.1 ms ± 26.2** | — |
| c | 398.0 ms ± 40.1 | 1.21× slower |
| rust (overflow-checks=on) | 401.9 ms ± 29.1 | 1.23× slower |
| rust | 410.7 ms ± 34.2 | 1.25× slower |
| go | 667.5 ms ± 23.6 | 2.03× slower |

**That 1.21× is the CPU baseline again, not codegen.** Same story as
[#260](../260-single-number-iii/): the fold vectorizes, `karac build` targets
`x86-64-v3` (AVX2) by default and `clang -O3` / `rustc -O` target `x86-64` v1.
Rebuilt at equal baseline, one hyperfine session, 20 runs:

| Lane (all at `x86-64-v3`) | mean ± σ |
|---|---|
| c `-march=x86-64-v3` | 312.4 ms ± 20.2 |
| kāra (default) | ~315 ms (1.01× behind c, inside σ) |
| rust `-C target-cpu=x86-64-v3` | 343.6 ms ± 32.6 |

**Kāra ties C and edges Rust at equal ISA baseline.** The honest one-line
summary is "parity on a vectorizable XOR fold", not a win.

Overflow checks are free here (`rust_ovf` 401.9 vs `rust` 410.7, inside σ) —
the loop is pure XOR, with no arithmetic to check beyond the loop counter.

Go's 2.03× is not a flag artifact: `gc` has no autovectorizer, so it runs
scalar against everyone else's SIMD.
