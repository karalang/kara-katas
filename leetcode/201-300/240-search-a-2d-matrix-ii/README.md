# 240. Search a 2D Matrix II

Search a matrix for `target`, where every row is sorted left→right **and** every
column is sorted top→bottom.

## Approach

Start at the **top-right** corner and walk a staircase:

- `matrix[r][c] == target` → found;
- `matrix[r][c] > target` → the whole column below is even larger, so step **left**;
- `matrix[r][c] < target` → the whole row to the left is even smaller, so step **down**.

Each step eliminates an entire row or column, so the walk visits at most `m + n`
cells → `O(m + n)` time, `O(1)` space. (Symmetric from the bottom-left corner.)

The matrix is passed as a flat row-major `Slice[i64]` with `rows`/`cols`, so
`matrix[r][c] = flat[r * cols + c]`.

**Workload.** Build-once + punch: a 1000×1000 doubly-sorted matrix built once as
a flat row-major array (8 MB, larger than L2), then 120 000 staircase queries. A
single query is only O(m + n), so the punch count is high rather than the matrix
being enormous. Targets straddle the value range: roughly half **hit** (exiting
early at varying depth) and half **miss** (running the full m + n staircase).
Benching only one would measure a single branch of the loop. Sink = `191408948`.

### Runtime — 30 runs, 5 warmup

| Lane | mean ± σ | vs kāra |
|---|---|---|
| go | 101.0 ms ± 14.7 | **4.32× faster** |
| rust | 429.8 ms ± 17.5 | 1.02× faster |
| c | 431.3 ms ± 17.1 | 1.01× faster |
| **kāra** | **436.7 ms ± 14.7** | — |
| rust (overflow-checks=on) | 442.2 ms ± 14.1 | 1.01× slower |

**Kāra ties `clang -O3` and `rustc -O`** — 436.7 vs 431.3 vs 429.8 ms, a 1.6%
spread against ~17 ms σ, so the three are indistinguishable. Overflow checks
are free (442.2 vs 429.8 ms).

### The Go outlier is real, and it is an LLVM-vs-Go-compiler story

Go is **4.3× faster than all three other compiled lanes**. That is exactly the
kind of surprising ranking that meant a broken mirror on
[#291](../291-word-pattern-ii/README.md), so it was checked before being
published:

- **Identical results.** All four lanes produce sink `191408948`.
- **Identical work.** Instrumenting the Go and C mirrors with a step counter
  gives **61 709 746 staircase steps each** — not approximately, exactly. Go is
  not taking a shortcut.
- **Not a cache effect.** Shrinking the matrix to 200×200 (320 KB, fits L2)
  leaves the gap essentially unchanged (C 0.27 s vs Go 0.08 s).
- **Not just the index multiply.** Hand-strength-reducing `r * cols` into an
  incrementally maintained row base speeds C up only 0.27 → 0.21 s, nowhere
  near closing it.

The suggestive part is *which* lanes cluster. **Kāra, Rust and C all go through
LLVM** and all three land within 2% of each other at ~430 ms; the single
non-LLVM compiler in the set is the one that is 4.3× faster. That points at
LLVM's handling of this particular data-dependent staircase loop rather than at
anything language-specific — and it means the kāra number here is not a kāra
weakness: kāra is exactly where its backend peers are.

The precise mechanism was not chased further, and this write-up does not claim
one. What is established is the list above: same answer, same step count, not
cache, not the multiply.
