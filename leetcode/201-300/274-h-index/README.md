# 274. H-Index

The h-index is the largest `h` such that at least `h` papers have at least `h`
citations each.

## Approach

Sort citations ascending. Then the papers at positions `[i, n)` are the `n − i`
most-cited; if `citations[i] ≥ n − i`, those `n − i` papers each have at least
`n − i` citations, so `n − i` is an achievable h-index. Scanning from the smallest
qualifying `i` yields the maximum such value. `O(n log n)`.

## Files

- [`h_index.kara`](h_index.kara) — Kāra implementation.
- [`h_index.py`](h_index.py) — Python mirror (oracle).

Expected output (both): `3 1 0 1 4 4` (one per line).

**Workload.** Build-once + punch: four 60,000-element citation arrays built
once, then 600 punches of the kata's `h_index` unchanged — copy into a fresh
vector, sort ascending, scan. The four arrays carry deliberately different
distributions so the sort sees more than one input shape: uniform-wide (30,000
distinct), uniform-narrow (40 distinct), heavily duplicated (7 distinct), and
nearly sorted. Sink = `854207143`, identical in all five languages.

### This kata measures stdlib sort quality, not codegen

Say that up front, because the numbers are lopsided and the reason is not
`karac`. Kāra's `Vec[i64].sort()` lowers to the runtime entrypoint
`karac_mir_sort_int` (`karac_vec_sort_i64_8` on the legacy backend), which **delegates to Rust's `sort_unstable`** —
pdqsort. So on this kata Kāra and Rust are literally running the same sort
implementation, and everything else in the lane is the surrounding copy, scan
and call overhead.

The Rust mirror therefore uses `sort_unstable`, not `sort`. Stable `sort` is a
different algorithm (allocating merge sort) and measures 590.3 ms ± 56.5 here —
using it would have handed Kāra a 1.8× "win" that is purely a choice of
`Vec` method.

| Lane | mean ± σ | vs kāra |
|---|---|---|
| **kāra** | **346.4 ms ± 8.2** | — |
| rust (`sort_unstable`) | 347.3 ms ± 24.7 | 1.00× |
| rust (overflow-checks=on) | 353.4 ms ± 5.4 | 1.02× slower |
| go (`slices.Sort`) | 1330.6 ms ± 46.2 | 3.84× slower |
| c (`qsort`) | 2471.8 ms ± 82.9 | 7.14× slower |

**Kāra and Rust are a dead tie** (1.00×), which is exactly what running the
same pdqsort should produce, and is the useful confirmation here: Kāra's copy
loop, bounds-checked scan and runtime call add nothing measurable around it.
(Container figure. On the M5, 2026-11-02, Kāra is 1.22× ahead of plain Rust — see
the table above.)

### C's 7.14× is `qsort`, and it is only half the story

`qsort` is idiomatic C and stays as the C lane, but its per-comparison
**indirect call** is not algorithm-matched against three monomorphised sorts.
Replacing it with a hand-rolled median-of-three introsort (insertion-sort
cutoff at 16, no callback) recovers most of it:

| C sort | mean |
|---|---|
| `qsort` (stdlib, indirect compare) | 2.48 s |
| hand-rolled introsort, monomorphised | **1.06 s** |

So ~2.3× of C's deficit is the callback, and the remaining 3.2× vs Kāra/Rust is
**pdqsort being a better sort than a textbook introsort** on these inputs — its
pattern-defeating heuristics take the nearly-sorted and 7-distinct-value arrays
in near-linear time, which median-of-three quicksort does not. Go's
`slices.Sort` is also a pdqsort and lands at 3.84×, so implementation quality
inside the same algorithm family spans a factor of four here.

None of that is a statement about the four compilers' code generation. It is a
statement about four standard libraries.
