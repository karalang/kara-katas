# 236. Lowest Common Ancestor of a Binary Tree

Given a binary tree and two present values `p` and `q`, return the value of their
**lowest common ancestor** — the deepest node having both as descendants (a node
is a descendant of itself).

## Approach

Unlike [#235](../235-lowest-common-ancestor-of-a-bst/) there is **no BST order**
to steer the search, so each node must inspect *both* subtrees. Classic recursive
post-order — each node reports what it found beneath it:

- an empty subtree, or a node that **is** `p` or `q`, reports itself upward;
- a node that gets a non-null answer from **both** children is the split point →
  it is the LCA;
- a node with only one non-null child answer forwards that answer up.

The first node to see the two targets arrive from different subtrees (or to be
one target with the other beneath it) is the LCA. `O(n)` time, `O(h)` stack.

The tree is an **index pool** (`Vec[Node]`, `i64` `left`/`right`, `-1` = null),
built from explicit `(val, left, right)` parallel arrays so *any* shape — not
just a BST — can be described.

## Files

- [`lca_binary_tree.kara`](lca_binary_tree.kara) — Kāra implementation.
- [`lca_binary_tree.py`](lca_binary_tree.py) — Python mirror (oracle).

Expected output (both): `3 5 5 2 3 3 1` (one per line).

**Workload.** Build-once + punch: one 100 000-node complete binary tree built as
an index pool, then 600 full recursive post-order LCA searches. Sink = `4189`.

**The contrast with [#235](../235-lowest-common-ancestor-of-a-bst/README.md) is
the point of benching both.** There, BST ordering lets the walk pick a direction
and finish in O(h) ≈ 35 steps, so it needs **8 000 000** queries to fill a
comparable runtime. Here there is no ordering to exploit, the recursion must
inspect *both* subtrees, and the cost is O(n) per query — so **600** queries
suffice. Same problem, same tree representation, three orders of magnitude apart
in per-query cost.

**Kāra beat both Rust configurations** on recursive tree traversal *in this

- the kāra lane moved 127.9 → 146.4 ms between two compilers whose
  **instruction counts differ by 0.002%**, at an identical 34,296-byte binary;

- five of six sibling katas are flat within 1% under the same compiler pair, so
  there is no across-the-board slowdown;
- the measured swing is **15.5%**, against the 16% placement spread this kata's
  own caveat already predicts.

So neither number is "the" result: this lane is placement-dominated, and the
kāra-vs-Rust comparison here is a tie whose sign is decided by which 64-byte
offset the recursion happens to land on. The analysis below is kept because it
explains the *shape* of the lane, which has not changed.

with 50 runs and warmup 8:

### An anomaly that reproduced: `rust_ovf` faster than `rust`

In both independent runs, Rust **with** overflow checks measured *faster* than
Rust without — 429.3 vs 507.7 ms, then 394.0 vs 450.5 ms on medians. Enabling a
check cannot make code faster, so on [#235](../235-lowest-common-ancestor-of-a-bst/README.md)
a similar 7% inversion was correctly dismissed as noise.

Here it is **13% and it reproduces across 80 measured runs**, which noise does
not. The plausible reading is a code-layout artifact: `-C overflow-checks=on`
changes inlining and block placement, and compiled performance is not monotonic
in added instrumentation — an unlucky layout for the plain build is entirely
possible on a recursive function this small.

The practical consequence for this table: the plain `rust` lane should be
treated as a slightly unlucky build, and **`rust_ovf` at 394 ms is the fairer
Rust figure** to compare kāra's 340 ms against. Kāra is ahead either way, which
is why both are shown rather than only the flattering one.
*2026-11-02: the inversion does not appear on the M5 — the two Rust rows tie
(139.8 vs 139.9 ms).*
