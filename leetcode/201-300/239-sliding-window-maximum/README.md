# 239. Sliding Window Maximum

Given `nums` and a window width `k`, return the maximum of every contiguous
window of size `k` as the window slides left to right.

## Approach

A naive per-window scan is `O(n·k)`. The **monotonic deque** method is `O(n)`:
keep a deque of *indices* whose values are strictly decreasing front→back, so the
front index always holds the current window's maximum.

- Before pushing `i`, pop from the **back** every index whose value is `≤ nums[i]`
  — none of them can be the max while `i` is in the window and at least as large.
- Pop from the **front** any index that has slid out of the window (`≤ i − k`).
- Once the first full window exists (`i ≥ k − 1`), the front index's value is that
  window's answer.

Each index is pushed and popped at most once → `O(n)` total.

The deque is a `Vec[i64]` of indices with an explicit `head` cursor: front-pop
advances `head`, back-pop is `Vec.pop()`, and the live span is `dq[head..len]`.

> **Host:** shared **x86-64 Linux cloud container**, committed as
> `bench/results.container-x86.json`, not `results.json` — the latter is
> reserved for canonical Apple M5 Pro numbers and is the only file
> `scripts/consolidate-bench.sh` feeds into the top-level chart. This kata has
> no M5 run, so it is deliberately absent from the consolidated feed. Only the
> **within-file cross-language ratios** are comparable.

**Workload.** Build-once + punch: 8 arrays of 50 000 LCG draws generated once,
then 300 punches of the monotonic-deque pass with window `k = 64`.

Data shape is load-bearing for this algorithm and was chosen deliberately. A
monotonically **rising** array makes every back-pop fire and holds the deque at
length 1; a **falling** one never pops and grows it to `k`. Either would
benchmark a degenerate case. LCG draws sit between them, so the back-pop loop
does a realistic variable amount of work per element.

The sink is **position-weighted** (`Σ (i+1)·max_i mod 1e9+7`) rather than a
plain sum, so a transposition in the output would change it — a plain sum would
accept a wrongly-ordered result. Sink = `11945225`, identical across all five
languages.

**Kāra is within 2% of Rust** — 294.1 vs 287.9 ms, comfortably inside the

checks are free (290.4 vs 287.9 ms).

This is the **tightest four-way clustering in the corpus so far**: every
compiled lane lands within 1.46× of the fastest. The algorithm is a pure
index-and-compare loop over a flat array with no hashing, no string handling
and almost no allocation, which removes every axis that separated the lanes on
the map- and string-heavy katas.

### Mirror-parity notes

- All five use an **array/slice plus head cursor** as the deque, matching the
  kata — not `VecDeque`, `container/list`, or `collections.deque`. A ring
  buffer would be a different structure.
- **C's advantage is allocation, not codegen.** Its deque and output are
  file-scope statics sized `N`, so it allocates nothing at all, while kāra,
  Rust and Go grow their vectors dynamically. That is most of the 1.32× gap.

The Python mirror is the correctness oracle, not a measured lane — it stays
behind the `KARA_BENCH_INCLUDE_PY` gate by design.
