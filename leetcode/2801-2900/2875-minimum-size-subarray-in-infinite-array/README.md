# 2875. Minimum Size Subarray in Infinite Array

You are given a **0-indexed** array `nums` and an integer `target`.

A **0-indexed** array `infinite_nums` is generated by infinitely
appending the elements of `nums` to itself.

Return *the length of the **shortest** subarray of the array*
`infinite_nums` *with a sum equal to* `target`*.* If there is no such
subarray return `-1`.

```
nums = [1,2,3],       target = 5  ->  2
nums = [1,1,1,2,3],   target = 4  ->  2
nums = [2,4,6,8],     target = 3  ->  -1
```

**Constraints:** `1 <= nums.length <= 10^5`; `1 <= nums[i] <= 10^5`;
`1 <= target <= 10^9`.

## Approaches

| file | mechanism |
|---|---|
| `infinite.kara` ★ | every whole copy of nums that fits in target is taken, n values each, and what is left, less than one copy's sum, is found as a window of nums laid twice end to end: every value is positive, so a sliding window finds the shortest run summing to it |
| `infinite_map.kara` | the whole copies as in the ★ arm; the rest found by prefix sums over nums laid twice, each sum kept in a `Map` with where it ends, a run summing to the rest found by looking up the prefix that rest short of the one now |
| `infinite_two.kara` | the rest without laying nums twice: a run summing to it either lies inside nums, or wraps, a suffix and a prefix, and then what it leaves out is a run inside nums summing to the total less the rest, as long as possible. One sliding window, returning a `(shortest, longest)` tuple, gives both |
| `infinite_search.kara` | the whole copies as in the ★ arm; the prefix sums of nums laid twice rise strictly, so for each start in the first copy `binary_search` finds the one end, if any, whose run sums to the rest, the lengths through `filter_map` and `min` |
| `infinite_solution.kara` | a Rust solution as LeetCode's Rust users write it: the whole copies counted in `i64`, then a sliding window over `r % n` up to `2 * n`, the best length kept as a `usize` from `usize::MAX`, carried to Kāra by `karac fix` |
| `differential.kara` | the five arms against the statement read literally, six properties |

Every arm prints the same 4 lines: LeetCode's three examples; 10^5
values, LeetCode's most, all 1 with target 10^9, all 10^5 with target

## Differential

`differential.kara` holds copies of the five arms and the statement
read literally: from every start in nums, the infinite array walked a
value at a time until its sum reaches target, the shortest walk that
hits target exactly kept. It draws 2000 random arrays of 1 to 6 values
from 1 to 5 with target 1 to 60, then 50 of up to 3000 values, every
other one from 1 to 10 and the rest up to 10^5, target up to 10^7, all
before any arm answers; the literal reading is asked only of the first
2000.

| | property |
|---|---|
| P1 | target up to 60, the answer is the literal reading's |
| P2 | target raised by one copy's sum: n more, or -1 still |
| P3 | the first value moved to the end: the same answer |
| P4 | nums reversed: the same answer |
| P5 | -1, or from 1 to target, and at least target over the largest value |
| P6 | each arm agrees with at least three of the other four |

The differential prints `2050 cases, lengths total 21176647: checksum
533231746, 61500 checks over 5 arms: 0 failures` under every lane in
Verification, and a Python reading of the same cases gives the same
checksum. On a failure it prints the first ten and then the count by
property.

## Verification

All five arms print the same output as `infinite.py` under `karac
__mir-run` (the v2 MIR interpreter), `karac __mir-llvm-run`, and `karac
__mir-llvm-asan` (AddressSanitizer and LeakSanitizer) with no error.
`karac run` and a `karac build` binary print the same output for them,

## Writing it

The four own arms checked clean as first written, `ends.get(..)` in an
`if let` and `binary_search(..).map(..)` inside `filter_map` among them.

LeetCode's Rust template took 18 `karac fix` edits in one run, the
wrapper included, and the diff shows these: `struct Solution {}` came
for the `impl`; `Vec<..>` became `Vec[..]` in both signatures; `|&x|`
lost its `&` twice and `Solution::` took `.`; `usize::MAX`, twice,
became `i64.MAX`, Kāra's lengths being `i64`; and the casts the widening
makes redundant went: `target as i64 / total` and `target as i64 %
total` lost theirs, as did `nums[r % n] as i64` twice, the `as usize` on
the quotient and the wrapper's `as i64` on the `i32` result. The `as
i32` casts on the returned lengths stay, narrowing that loses nothing,
every answer being at most 10^9.
