# 129. Sum Root to Leaf Numbers

> **Difficulty:** Medium &nbsp;·&nbsp; **Topics:** Tree · DFS &nbsp;·&nbsp; **Source:** [leetcode.com/problems/sum-root-to-leaf-numbers](https://leetcode.com/problems/sum-root-to-leaf-numbers/)

Each root-to-leaf path spells a base-10 number (digits top to bottom). Return the sum over all such paths.

```
    1            4               1·2 = 12, 1·3 = 13  -> 25
   / \          / \
  2   3        9   0             4·9·5=495, 4·9·1=491, 4·0=40 -> 1026
              / \
             5   1
```

**Constraints:** node count `1..1000`, each `0 ≤ node.val ≤ 9`.

## Approaches

| Approach | Kāra | Python |
|---|---|---|
| **DFS with a running path-number** ★ | [`sum_numbers.kara`](sum_numbers.kara) ✓ | [`sum_numbers.py`](sum_numbers.py) ✓ |

`✓` runs end-to-end today: interpreter, JIT, and codegen (default auto-par and `KARAC_AUTO_PAR=0`) all agree with the Python mirror. Validated against the known answers (25, 1026, single-node 7). Zero diagnostics, valgrind-clean.

## The mechanism

One DFS carrying a running value `cur = cur * 10 + node.val` down each branch; at a leaf, `cur` **is** the path number, so it is returned directly, and internal nodes sum their two subtrees. O(n), O(h) stack. Node type is the `shared struct TreeNode` (RC) shared with [#112](../112-path-sum/)/[#124](../124-binary-tree-maximum-path-sum/).

**Workload.** Build-once + punch: four balanced 2047-node trees built once, then
40 000 full root-to-leaf DFS traversals. Sink = `596693765`.

**Depth is bounded on purpose.** Each path spells a base-10 number
(`cur = cur*10 + val`), so a depth-18 tree produces path numbers near 1e18 and
the sum over its leaves overflows i64 outright — kāra traps overflow by default,
so the benchmark would have aborted rather than measured. At depth 11 the leaf
sum stays near 1e14. The punch count carries the workload instead of the tree
size.

### Why: this kata measures reference counting, and kāra elides it

This is the corpus's only tree kata built from a **`shared struct`** — kāra's
reference-counted type — rather than an index pool. The mirrors were written to
match each language's honest equivalent, which makes the RC cost visible:

| Lane | ownership model | pays retain/release in the traversal? |
|---|---|---|
| kāra | `shared struct` (RC) | yes — but see below |
| rust | `Rc<TreeNode>` | **yes** |
| go | GC'd `*TreeNode` | no |
| c | raw `malloc`'d pointer | no |

Rust's 1.58× deficit (container; 1.51× on the M5) is not a codegen failure — it is `Rc` clone/drop traffic on
every recursive descent, which is the correct mirror of kāra's `shared struct`.
Go and C simply do not pay it.

**Kāra pays it too, and then optimizes it away.** Rebuilding with the RC-elision
pass disabled isolates the effect exactly:

Container session; not part of `bench.sh`'s feed, so not re-run on the M5.

| Build | mean ± σ | |
|---|---|---|
| kāra, RC elision **ON** (default) | 224.2 ms ± 8.0 | ties C |
| kāra, RC elision **OFF** (`KARAC_RC_ELIDE_REF_PARAMS=0`) | 342.6 ms ± 17.2 | ties Rust's `Rc` |
| rust (`Rc`) | 328.3 ms ± 15.7 | — |
| c (raw pointer) | 214.5 ms ± 11.9 | — |

**RC elision is worth 34.6% on this kata**, and the two numbers land exactly
where the model predicts: with elision off, kāra (342.6 ms) sits alongside
Rust's `Rc` (328.3 ms) — both paying full refcount traffic; with it on, kāra
(224.2 ms) sits alongside raw-pointer C (214.5 ms) — neither paying any. Both
builds produce the identical sink.

That 34.6% is slightly above the 17–32% range the compiler's own notes claim for
this optimization on read-only tree walks, which is a reasonable place for a
DFS that touches every node and does almost nothing else.

## Kāra features exercised

- **`shared struct TreeNode` (RC)** post-order-style DFS over `Option[TreeNode]`, borrowing each child.
- **Leaf detection via `match n.left { None => … }`** — the two-child `None` test that distinguishes a leaf from an internal node.
- **Overflow-checked digit accumulation** — `cur * 10 + val` under kāra's default trap; the modular sink fold keeps the digest in i64.
