# 134. Gas Station

> **Difficulty:** Medium &nbsp;·&nbsp; **Topics:** Array · Greedy &nbsp;·&nbsp; **Source:** [leetcode.com/problems/gas-station](https://leetcode.com/problems/gas-station/)

`n` stations in a circle; `gas[i]` fills the tank, `cost[i]` is the gas to reach `i+1`. Return the starting index from which you can complete the loop once (unique if it exists), else `-1`.

```
gas=[1,2,3,4,5], cost=[3,4,5,1,2]  ->  3
gas=[2,3,4],     cost=[3,4,3]      -> -1
```

**Constraints:** `1 ≤ n ≤ 10⁵`, `0 ≤ gas[i], cost[i] ≤ 10⁴`.

## Approaches

| Approach | Complexity | Kāra | Python |
|---|---|---|---|
| **Greedy single pass** ★ | O(n) time, O(1) space | [`gas_station.kara`](gas_station.kara) ✓ | [`gas_station.py`](gas_station.py) ✓ |

`✓` runs end-to-end today: interpreter, JIT, and codegen (default auto-par and `KARAC_AUTO_PAR=0`) all agree with the Python mirror. Validated against known cases (3, -1, single-station 0) plus deterministic-LCG inputs. Zero diagnostics, valgrind-clean.

## The mechanism

Two running sums in one pass. `total` accumulates `gas[i] - cost[i]` over the whole ring — the trip is feasible iff `total ≥ 0`. `tank` is the running balance from the current candidate start; the moment it dips below zero, **no** station from the candidate up to `i` can be the true start (each was reached with non-negative tank, so dropping the prefix only helps), so the candidate jumps to `i + 1` and `tank` resets. The last surviving candidate is the unique answer. O(n), O(1).

**Workload.** Build-once + punch: eight gas/cost array pairs of 200 000 elements

Half the pairs are **feasible** (costs drawn from a smaller range than gas) and
half are not. Both walk the entire array — the algorithm has no early exit — but
they differ in how often the `tank < 0` restart fires, which is the only branch
in the loop.

**The tightest four-way spread in the corpus: 1.11× from fastest to slowest.**
Kāra ties `rustc -O` exactly (439.8 vs 442.7 ms — 0.7% apart against σ of 38.5
and 36.4, so indistinguishable) and sits within 10% of `clang -O3`.

This is what a benchmark looks like when there is nothing left to differentiate
the backends: one linear pass over two flat `i64` arrays, one subtraction, two
adds and one predictable branch per element, no allocation, no hashing, no
indirection. Every lane is memory-bandwidth-bound on the same 3.2 MB of data,
and every lane lands within noise of the others.

Peak RSS is essentially identical too — 26.6 / 26.6 / 26.0 / 26.5 MiB — because
the arrays *are* the working set and no lane adds meaningful overhead on top.

The `rust_ovf` lane measuring 3% *faster* than plain `rust` is noise (both
inside σ), the same benign inversion recorded on
[#235](../../201-300/235-lowest-common-ancestor-of-a-bst/README.md) and
distinct from the reproducible 13% one on
[#236](../../201-300/236-lowest-common-ancestor-of-a-binary-tree/README.md).

### Mirror-parity note

The bench passes the arrays **by reference**, where the kata's `can_complete`
takes `Vec[i64]` by value. By value would copy 200 000 elements per call —
work no mirror performs, and enough to swamp the O(n) scan being measured.

## Kāra features exercised

- **Two owned `Vec[i64]` inputs** consumed by value into the greedy scan (`gas[i] - cost[i]`).
- **`mut ref i64` sink accumulator** threaded into a `report` helper (`report(g, c, mut sink)` — the fresh-binding call-site `mut` marker).
- **Overflow-checked running sums** — `total` / `tank` under kāra's default trap.
