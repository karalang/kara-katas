# 131. Palindrome Partitioning

> **Difficulty:** Medium &nbsp;·&nbsp; **Topics:** Backtracking · DP · String &nbsp;·&nbsp; **Source:** [leetcode.com/problems/palindrome-partitioning](https://leetcode.com/problems/palindrome-partitioning/)

Return **all** ways to cut `s` into contiguous pieces such that every piece is a palindrome.

```
"aab"  ->  [["a","a","b"], ["aa","b"]]          (2 partitionings)
"aaaa" ->  8 partitionings
```

**Constraints:** `1 ≤ s.length ≤ 16`, lowercase.

## Approaches

| Approach | Kāra | Python |
|---|---|---|
| **Backtracking over palindromic prefixes** ★ | [`palindrome_partitioning.kara`](palindrome_partitioning.kara) ✓ | [`palindrome_partitioning.py`](palindrome_partitioning.py) ✓ |

`✓` runs end-to-end today: interpreter, JIT, and codegen (default auto-par and `KARAC_AUTO_PAR=0`) all agree with the Python mirror. Answers are validated against the known counts (aab 2, aaaa 8, single 1). Zero diagnostics, valgrind-clean.

## The mechanism

Backtrack from index `start`: for each `end ≥ start`, if `s[start..=end]` is a palindrome, push that piece onto the running `path`, recurse from `end + 1`, then pop (undo the choice). A complete cut is reached when `start` walks off the end. To keep the oracle deterministic without pinning a partition order, each complete cut contributes to a `count` and an **order-independent digest** (sum of per-partition hashes). The palindrome test is a two-pointer byte scan on the inclusive range; each piece is materialized as a fresh substring.

**Workload.** Build-once + punch: four 16-character case strings built once,
then 150 punches of the full backtracking enumeration. Sink = `469710171`,
identical across all five languages.

**String shape *is* the workload.** An all-`'a'` string of length n has
2^(n−1) palindromic partitionings, so the search is exponential in n and two
extra characters change the runtime fourfold. The set deliberately mixes:

| Case | Branching |
|---|---|
| `aaaaaaaaaaaaaaaa` | maximum — every substring is a palindrome |
| `abababababababab` | moderate |
| `aabaacaabaacaaba` | structured, irregular |
| `abcdefghijklmnop` | minimum — only single characters are palindromes |

Benching only the all-`'a'` case would measure one extreme of the search tree.

Overflow checks cost Rust 12% (261.6 → 293.5 ms), a middling figure: this
workload does per-character arithmetic in the hash but spends most of its time
allocating and copying substrings. Compare [#242](../../201-300/242-valid-anagram/README.md)
where the same flag cost 1.87× on a purely arithmetic loop, and
[#130](../130-surrounded-regions/README.md) where it was exactly free.

### Why kāra is behind: per-piece `String` allocation

The measured cost is dominated by `substring` — called once per palindromic
piece at every node of the search tree, tens of thousands of times per punch,
each producing a fresh heap `String`. This is the same axis
[#332](../../301-400/332-reconstruct-itinerary/README.md),
[#290](../../201-300/290-word-pattern/README.md) and
[#291](../../201-300/291-word-pattern-ii/README.md) identified: kāra is
competitive on array, grid and tree work but pays more than its peers on
**heap-`String` churn**. Four katas now agree on that, which makes it a
characteristic rather than a one-off.

### Mirror-parity note

The kata's `substring` is **O(n)** — it walks `s.chars()` and filters, rather
than slicing. Every mirror reproduces that, including C (`for` over the string,
not `memcpy`), Rust (`.chars().enumerate()`, not `&s[lo..=hi]`) and Go
(`range s`, not `s[lo:hi+1]`). Letting those lanes use their native O(1) slice
would have made them a **different algorithm** and would have inflated kāra's
apparent deficit considerably.

## Kāra features exercised

- **Backtracking with a `mut ref Vec[String]` path** — `push` a palindromic piece / recurse / `pop`; `count` and `digest` ride alongside as `mut ref` out-params (the same shape as [#126](../126-word-ladder-ii/)/[#124](../124-binary-tree-maximum-path-sum/), forwarded through recursion without a call-site marker).
- **Substring materialization** — `s[start..=end]` built char-by-char from `s.chars()`; each piece is an owned `String` pushed onto the path and freed on `pop`/scope exit (leak-clean on the `Vec[String]` path — the class `B-2026-07-18-52` closed).
- **Two-pointer palindrome test** over `s.bytes()` on an inclusive index range.
